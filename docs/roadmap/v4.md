# v4 Roadmap — From Reviewer to Autonomous Engineering Agent

> **Status:** Exploratory — not committed. This is a directional document for thinking through what Ryv becomes after v3 is fully shipped.
> **v3 premise:** All Phase 1–3 features are live — graph-aware review, multi-agent orchestration, test generation, CI analysis, agentic fix PRs, GitLab support, MCP integrations, rules system, /ask, CLI pre-push, everything.
> **v4 thesis:** Ryv stops waiting to be triggered and starts working on your behalf.

---

## The Version Progression

```
v2  →  Ryv understands your codebase graph
v3  →  Ryv acts on every PR (review, test gen, fix, CI analysis, rules)
v4  →  Ryv works proactively, across repos, without needing a PR trigger
```

The shift from v3 to v4 is the shift from **tool** to **teammate**.

A tool waits. A teammate is already working when you arrive.

---

## What's Still Missing After v3

v3 ships feature parity with every competitor and surpasses them on graph intelligence. But three fundamental limitations remain:

**1. Ryv is entirely reactive.** Every capability in v3 fires only when a PR is opened or updated. Nobody asked Ryv to watch your codebase between PRs and report what it's seeing. Every other AI agent in adjacent industries (SRE, data pipelines, infrastructure) has moved past this.

**2. Ryv knows nothing across repo boundaries.** The symbol graph is per-repo. When `service-a` changes a shared DTO, `service-b` finds out only when a broken PR is submitted — after the fact. The real value of a codebase map is knowing the blast radius across the entire org, not just within a single repo.

**3. Ryv lives only in PR threads and the web dashboard.** Engineers spend most of their time in their IDE and terminal. Ryv is absent from both. By the time a PR is open, the code is already written.

v4 addresses all three.

## Theme 1 — Proactive Intelligence

> Ryv watches your codebase continuously and reports what it sees — no PR needed.

### 1.1 Codebase Health Reports

A scheduled job (daily or weekly, configurable) that scans the symbol graph and surfaces risk patterns:

```
📊 Weekly Codebase Health — Ryv Report
repo: api-service  branch: main  generated: Mon 2 Mar 2026

⚠️  5 high-blast-radius functions with zero test coverage
     payment.ts:ChargeService.processRefund  (blast radius: 23 callers)
     auth.ts:TokenValidator.verify           (blast radius: 18 callers)
     ...

🔴  3 functions changed more than 8 times in 30 days with no spec file
     checkout.ts:CartService.applyDiscount   (12 changes, 5 authors)
     ...

💀  7 exported symbols with no callers anywhere in the codebase
     legacy/converter.ts:LegacyXmlParser     (last touched: 14 months ago)
     ...

🔒  2 functions touching auth or payments with a new external dependency
     added last week: stripe-webhook-validator@2.3.1 → payment.ts
```

Delivered as:
- A PR comment on a designated tracking PR (GitHub/GitLab/Azure)
- A dashboard notification
- Slack / Teams webhook (configurable)

This requires zero user action. Ryv is doing work that previously required a dedicated eng-metrics platform.

### 1.2 Drift Alerts

When the symbol graph changes significantly between two main-branch snapshots — functions added/removed, edges rerouted, blast radius scores crossing thresholds — Ryv posts an alert before any PR is linked to the change.

Example trigger: `CartService.applyDiscount` blast radius jumps from 4 to 31 callers after a merge to main. Ryv alerts the owning team immediately.

### 1.3 Hotspot Prediction

A heuristic model (no ML required) that scores each file as a predicted incident source:

```
hotspot_score = (churn_30d × blast_radius × (1 - test_coverage)) / author_count
```

Files in the top 10% of this score are flagged in the health report. This is a git-signals-meets-graph-intelligence feature — everything needed already exists in the Ryv data model.

## Theme 2 — The Agentic Layer

> Ryv stops only commenting and starts opening PRs.

v3 ships agentic fix PRs triggered by a review. v4 extends this to proactive, scheduled, and user-initiated agent actions that don't require an existing PR.

### 2.1 `/fix` — Autonomous Fix PR

A slash command (in PR thread, dashboard chat, or CLI) that instructs Ryv to:

1. Take a specific comment or rule violation
2. Apply the fix to the codebase
3. Run the suggestion validator (tree-sitter syntax check)
4. Run the test suite against the patch
5. Open a companion PR with the change

This exists partially in v3 (fix suggestions in reviews). v4 makes it a first-class, standalone workflow — not dependent on an active review.

### 2.2 `/refactor` — Graph-Guided Refactoring

Ryv identifies refactoring opportunities using the symbol graph — patterns that only become visible when you can see the whole graph at once:

- **Dead code removal:** symbols with zero callers across all repos
- **Duplicate logic:** two functions in different modules with high embedding similarity and the same callers
- **Blast radius reduction:** a function called by 40 callers that could be split into two functions each called by 20, reducing incident blast radius by half
- **God object detection:** a class with 30+ methods referenced from 50+ files — suggests decomposition

Ryv opens a draft PR for each opportunity. Engineer reviews and merges or dismisses.

### 2.3 Autonomous Test Coverage Agent

Scheduled or triggered. Ryv:

1. Queries the health report: which functions have high blast radius and zero tests?
2. Generates a test file for each, targeting the blast-radius callers specifically
3. Validates the generated tests compile and pass
4. Opens a PR with a title like `test: add coverage for ChargeService.processRefund (blast radius: 23)`

This is the test generation feature from v3 — made proactive. Instead of a developer having to run `/test`, Ryv fills coverage gaps on its own schedule.

## Theme 3 — Cross-Repo Org Graph

> The symbol graph expands from one repo to the whole org.

### 3.1 Cross-Repo Symbol Resolution

When `service-a` imports `UserDTO` from a published internal package `@acme/contracts`, Ryv resolves that import across repo boundaries and builds a cross-repo edge:

```
service-a:PaymentService.charge
  → calls →
service-b:AuthService.validateUser  (cross-repo edge via @acme/contracts)
```

This requires:
- Package registry scanning (npm, pip, Maven) — or direct source linking for monorepos
- Cross-repo `VCSAdapter` calls to index dependency packages
- A new `cross_repo_edges` table in Postgres

### 3.2 Service Interface Tracking

Track typed interface contracts as first-class graph nodes:

- **OpenAPI schemas** — parse `openapi.yaml`, extract request/response types as symbols
- **gRPC protos** — parse `.proto` files, extract services and message types
- **GraphQL schemas** — parse `schema.graphql`, extract types and resolvers

When any of these interface definitions change, Ryv automatically:

1. Computes the downstream consumers (all repos importing that interface)
2. Posts a cross-repo blast radius warning to every PR that touches the change
3. Optionally opens update PRs in consumer repos if the change is additive and auto-applicable

### 3.3 Org-Wide Blast Radius

The blast radius score becomes org-scoped:

```
service-a:ChargeService.processRefund
  Direct callers (same repo):  8
  Callers via @acme/payments:  12 (in service-b, service-c)
  Callers via REST API:         4 (in mobile-app, web-client)
  Total org blast radius:      24  ← v4 shows this
```

This is the feature that makes Ryv genuinely irreplaceable for platform and infrastructure teams.

## Theme 4 — IDE Integration

> Ryv moves left — into the editor, before the PR exists.

### 4.1 VS Code Extension

A language server-style extension that:

- Shows blast radius inline next to function definitions (as a code lens): `⚡ blast radius: 14`
- Highlights uncovered high-blast-radius functions with a warning gutter icon
- Shows the `callers` / `callees` panel in a sidebar on hover
- Runs a lightweight, local review when you save a file (using the CLI pre-push pipeline)

The extension queries the Ryv API — it does not run Tree-sitter locally. The symbol graph already exists; the extension is just a rendering layer on top of it.

### 4.2 JetBrains Plugin

Same feature set as VS Code, targeting IntelliJ IDEA, PyCharm, GoLand.

### 4.3 MCP Server (Expose Ryv to AI Assistants)

Expose the symbol graph and review pipeline as an MCP server, so any MCP-capable client (Claude Desktop, Cursor, Cline, etc.) can query Ryv directly:

```
Tools exposed via MCP:
  ryv_blast_radius(symbol)    → returns callers, callees, risk score
  ryv_search_symbols(query)   → semantic search across the org graph
  ryv_run_review(diff)        → run review pipeline, return comments
  ryv_get_rules()             → fetch active team rules for current repo
  ryv_health_report(repo)     → fetch latest health report
```

This is potentially the highest-leverage v4 feature. Every AI coding assistant becomes graph-aware by calling Ryv as a tool. Ryv's symbol graph becomes org-wide shared context.

## Theme 5 — Intelligence Compounding

> The more Ryv is used, the smarter it gets about your specific codebase.

### 5.1 Auto Best Practices Distillation

Scheduled job (monthly or configurable):

1. Fetch all accepted review comments from the last period
2. Cluster by embedding similarity (pgvector k-means or hierarchical)
3. For each cluster with 3+ similar accepted comments, propose a new named rule via dashboard notification: `Suggest adding rule: "Always validate stripe webhook signatures before processing"`
4. Engineer approves/rejects — approved rules enter the rules system automatically

Closes the loop: review insights compound into permanent team standards without manual effort.

### 5.2 Ownership Graph

Derived from git history + review engagement:

```typescript
interface OwnershipRecord {
  symbolId: string;
  primaryOwner: string;          // highest commit + review activity
  contributors: string[];
  lastTouchedBy: string;
  confidenceScore: number;       // how concentrated ownership is (0 = shared, 1 = solo)
}
```

Used in two places:
- **Review routing:** When Ryv posts a review, it `@mentions` the primary owner of the blast radius symbols
- **Health reports:** "This function has a `confidenceScore` of 0.95 — sole owner has been on leave for 3 weeks"

### 5.3 Incident Feedback Loop

When a production incident is tagged in PagerDuty/Opsgenie/GitHub Issues, Ryv:

1. Matches the incident to the last PR that touched the affected service
2. Records the incident against the review comments from that PR
3. Upweights similar patterns in future reviews — "this class of comment has a track record of catching real incidents"

This is a primitive form of reinforcement learning on the feedback loop — done entirely with the existing pgvector + rules infrastructure, no ML training required.

## What NOT to Build in v4

| Feature | Why Not |
|---|---|
| **Cloud billing / SaaS tier** | Self-hosted is the positioning. Hosting costs belong to the customer. |
| **Custom LLM fine-tuning** | Prompt engineering + RAG is cheaper, faster, and doesn't lock to one model |
| **Slack/Teams chatbot interface** | MCP server covers conversational use cases without a separate integration |
| **Pull request merge gates (blocking)** | Ryv advises; engineers decide. Blocking creates adversarial relationship with the tool |
| **Code execution / sandboxes** | Out of scope — test running belongs to CI, not to the reviewer |
| **monday.com / Gerrit** | Wrong ICP |

## Suggested Build Sequence

### Sprint 0 — Harness Engineering (Do This First)

> **Plan:** `docs/plans/harness-engineering.md`
> **Effort:** 1–2 days for Tasks 1–5 / 2–3 days for Task 6 (dashboard)
> **Rationale:** Pure prompt + middleware changes. Zero new infrastructure. Measurably improves review quality before any v4 feature ships. Establishes the acceptance-rate baseline needed to measure everything else.

Inspired by LangChain's finding that moving rank 30 → 5 on a coding benchmark required only harness changes — no model change. Ryv has the same improvement surface.

| Task | What | File | Effort |
|---|---|---|---|
| 1 | **Adversarial self-reflection** — change scoring task from "assess" to "try to disprove" | `self-reflection.ts` | 30 min |
| 2 | **Context manifest header** — tell each agent exactly what data it has and that it must use all of it | `prompt.ts` | 1 hr |
| 3 | **Pre-completion checklist** — force agents to verify they checked callers, rules, and tickets before submitting | `prompt.ts` | 1 hr |
| 4 | **Per-agent reasoning budget** — security/correctness at `temp=0.3`, style at `temp=0.4`, compliance at `temp=0.1` | `multi-agent.ts` | 1 hr |
| 5 | **Within-agent semantic dedup** — apply `themeDedupeComments()` per-agent before Judge, not only after merge | `multi-agent.ts` | 2 hrs |
| 6 | **Agent Quality Report** — dashboard tab: per-agent acceptance rate, rejection pattern analysis, trend over time | API + dashboard | 2–3 days |

**Body Injection + Graph-Scoped Search** (build together, they share `StorageAdapter.fetchBodies()`):

| Task | What | Plan | Effort |
|---|---|---|---|
| 7 | **Symbol body injection** — add `body TEXT` column, extract at index time, inject direct caller/callee bodies into prompt | `docs/plans/symbol-body-injection.md` | 6 hrs |
| 8 | **Graph-scoped pattern search** — `PatternSearcher` class, find call sites in stored bodies, classify return handling (`⚠️ unchecked` / `✅ null-checked`), inject structured table into prompt | `docs/plans/graph-scoped-search.md` | 6 hrs |

Tasks 7 and 8 share a dependency (the `body` column + `fetchBodies()` method). Build task 7 first, then task 8 runs on top of it.

Tasks 1–5 ship together. Task 6 is standalone. Tasks 7–8 are the second batch.

## Definition of Done for v4

A team using Ryv in v4:

1. **Gets a weekly health report** in their main branch PR without doing anything — untested blast-radius functions, churn hotspots, dead code.
2. **Asks Ryv questions from Cursor/Claude Desktop** via MCP without opening the dashboard.
3. **Sees blast radius scores inline in VS Code** while editing, before writing the PR description.
4. **Has Ryv open a test PR automatically** for high-risk untested functions it identified.
5. **Gets a cross-repo warning** when a shared DTO change would break a downstream service.
6. **Watches rules grow automatically** as accepted review comments compound into team standards.

At v4 complete, Ryv is not a code review tool that developers use. It is a codebase intelligence layer that is always running.
